# smart-charge-decision-service

Collectus hackathon — **the AI decision gate** for Smart Autocharge.
Stateless brain: features in → `{action, amount, score, reason}` out.

```
Frontend → rpm-autopay-service ──POST /v1/decide──▶ smart-charge-decision-service
                    │                                   (trained model + policy)
                    └── Autopay (if charge)
```

## How it decides

1. **Hard gates** — no overdue, attempt cap (`fails_7d ≥ 5`), no declines left this month,
   duplicate `event_id` (idempotent replay).
2. **Model** — logistic regression trained on 20k historical autocharge attempts
   (`data/historical_charges.csv`) predicts **P(success)** of charging the full overdue now, from
   card health, recent success, 7-day fails, days overdue, repayment just made, payday window and
   **card type**: network (Mada / Visa / Mastercard), wallet (Apple Pay / plastic) and funding
   (debit / credit / prepaid).
3. **Full-charge gate** — charge the full overdue if P clears the bar, otherwise skip and keep the
   decline for a better moment. The bar depends on the card's scheme declines left this month
   (Mada 3, Visa/Mastercard 6):

| Declines left | Repayment moment | Scheduled cron day |
| --- | --- | --- |
| 3 or more | 5% | 5% |
| 2 / not sent | 10% | 10% |
| 1 (last) | 30% | 50% |
| 0 | skip (hard gate) | skip (hard gate) |

4. **Explanation** — top feature drivers (coef × standardized value) in the reason string, plus
   the next best action when it skips (update card, wait for payday, save the decline…).

Why no partials? The 30-day backtest showed partial charges at the repayment moment don't pay off:
the remainder falls back to cron, which charges on a worse day and fails. The repayment moment is
usually the customer's best chance all month, so charge it in full; spend AI judgement on whether a
decline is worth using. The expected-value partial policy is still available with
`REPAYMENT_POLICY=expected_value`.

Send `features.declines_left` and the card fields (`card_network`, `card_token`, `card_funding`);
omitted card fields mean Mada, plastic, debit. The reason names the card ("Repayment moment on a
Visa credit Apple Pay: …"). Human-set limits always sit above the model.

## Historical data

Synthetic but structured like the real thing: one row per past autocharge attempt with
PM health, recent success, 7-day fails, days overdue, repayment just made, charge size,
trigger (`cron` vs `event`), payday window, **card network / wallet / funding**, outcome and
decline code. Generated by `app/world.py` from a hidden ground-truth formula the model has to learn.
Card effects are invented (Apple Pay and credit help, prepaid hurts, Visa slightly lower than Mada),
not real Tamara rates. Swap in real autocharge history with the same columns for production.

In the synthetic history: Apple Pay 37% vs plastic 31% success; credit 40%, debit 33%, prepaid 18%.
Model AUC **0.82**.

## Quick start

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
uvicorn app.main:app --reload --port 8001
```

Docs: http://127.0.0.1:8001/docs · Tests: `pytest -q`

The model trains automatically on first start (≈1s). Regenerate data with
`python -m scripts.generate_history --rows 20000 --seed 42`.

### Wire into the backend

In `rpm-autopay-service/.env`:

```
USE_MOCK_AI=false
AI_DECISION_URL=http://127.0.0.1:8001/v1/decide
```

## APIs

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/v1/decide` | Decision for a `repayment.succeeded` event (contract used by backend) |
| POST | `/v1/backtest/month` | 30-day simulation with decline budgets: 5 strategies incl. a simple non-AI rule |
| POST | `/v1/backtest` | One moment: cron vs always-charge vs active policy |
| GET | `/v1/model` | Version, coefficients, AUC/Brier, history stats, policy limits |
| POST | `/v1/model/retrain` | Retrain from history |
| GET | `/health` | Health + model version |

### Example

```json
POST /v1/decide
{
  "event_id": "evt_1", "customer_id": "c_recover_001",
  "amount_paid": 249.75, "overdue_amount": 249.75,
  "features": {"days_overdue": 14, "pm_health": 0.5, "fails_7d": 3,
               "recent_success": 0.4, "repayment_strength": 1.0, "declines_left": 1}
}
→ {
  "action": "skip", "amount": 0.0, "score": 0.19,
  "reason": "Repayment moment: P(success) 19% is below the 30% bar — skip and keep the decline for a better moment. Decline budget: 1 left this month, so the bar is 30%. Drivers: …",
  "next_best_action": "Save the last 1 decline(s) for a stronger moment: next repayment or payday window",
  "drivers": [...], "candidates": [...], "declines_left": 1, "min_success_prob_applied": 0.3
}
```

## One-pass backtest (single moment)

`POST /v1/backtest` compares cron, always-charge and the active policy at one moment. Over a month
the picture is different — use the 30-day backtest below.

## 30-day backtest (2,000 customers, mixed cards, 3 seeds)

Each customer gets a card (55% Mada, 33% Visa, 12% Mastercard), repayment events on random days,
cron on D0/D3/D18/D29, one decline per day max, and a monthly decline budget by network
(Mada 3, Visa/Mastercard 6). Same customers and luck for every strategy.

| Strategy | Recovered | Failed attempts | Out of declines |
| --- | --- | --- | --- |
| Cron only (today) | 44.1–47.1% | ~4,420 | ~32% |
| Cron + always charge on repayment | 51.2–52.0% | ~4,470 | ~32% |
| Cron + simple rule on repayment (non-AI) | 49.5–51.0% | ~4,390 | ~31% |
| Cron + smart partials on repayment | 47.2–50.3% | ~4,510 | ~32% |
| **Full charge on repayment + AI-gated cron (live policy)** | **49.9–51.7%** | **~3,140** | **~5%** |

Vs cron only: about +12% recovered and ~29% fewer failed attempts. Vs always-charge or a simple
rule: within ~0.5–1 point of the recovery with ~30% fewer failed attempts. Synthetic simulation,
not real data.
